# 新文章自动分发

作者继续在 Pages CMS 写文章。关闭「草稿」并保存后，Cloudflare Pages 部署网站，Buffer 把文章送到指定的 X 账号，Brevo 从中文专用 RSS 生成 Newsletter。Facebook Page 可以单独添加。日常发文沿用现有标题、摘要、发布日期和可选封面。

本 PR 默认关闭发送。基线为 `null`，两个 GitHub 发送开关均默认为关闭，Brevo 需要在账户中独立配置。真实邮件、社交发帖和启用生产自动化均需作者授权。

## 补丁审查

| 原实现 | 仓库和官方文档核对 | 本次处理 |
| --- | --- | --- |
| 取单次 push 前后的 Git diff | Pages CMS 新文章默认草稿，可直接保存为公开。Astro 缺省 `draft: false`。取消或丢失单次工作流后，后一次 diff 无法找回前次文章 | 扫描当前 `main` 的第一父历史，识别首次公开。push 与每 3 小时补偿共用同一个扫描流程 |
| 文件名等同永久身份，关闭 rename 检测 | `urlName` 是 CMS 文件名输入。Astro 从文件路径生成 collection ID，`/${lang}/${post.id}/` 直接影响路由、canonical 和原 RSS GUID。双语 `translationId` 只用于配对 | 文件创建时产生分发 ID，沿 Git 重命名和登记的路径别名保留。中文与英文版本有各自的分发 ID |
| 最近 50 条 Buffer 帖子以链接或标题去重 | 旧帖会滚出范围，重复标题和短链会误判。Buffer 接受请求也可能丢失响应 | 独立 Git 账本按分发 ID 和渠道 ID 记录。在调用变更接口前持久化尝试记录，取得 Post ID 后按 ID 核实 |
| 等生产页面 HTTP 200 和 canonical | Cloudflare 由 Git 集成独立部署。旧页面或回滚页面也可能返回相同 canonical | 先读取生产版本索引，匹配基线、文章版本和 URL，再检查页面 canonical |
| 近似 X 加权字符和广泛的渠道判断 | 复杂 ZWJ emoji、旗帜和组合字符不能按码点相加。Buffer 当前 schema 支持 X 的正文链接及 Facebook 的 `linkAttachment` | 保留标题、摘要、标签和链接的生成流程。采用 `twitter-text` 计数，按字素截断。只接受明确配置的 X 和 Facebook |
| `npm ci --ignore-scripts` 并导入 YAML 库 | `js-yaml` 已在 `package.json` 和锁文件直接声明，现有 `npm test` 会构建后运行 `scripts/*.test.mjs` | 锁定 `twitter-text`，沿用原有测试入口。发送 job 只安装脚本所需依赖 |
| 主要覆盖 Buffer | 线上 `/zh/rss.xml` 验证时提供 26 篇文章，GUID 取 canonical，没有封面 enclosure。源码会包含历史和未来日期的公开文章 | 保留读者 RSS，新增中文 `/zh/distribution.xml` 给 Brevo |

参考 [Astro content collections](https://docs.astro.build/en/guides/content-collections/)、[Astro RSS](https://docs.astro.build/en/recipes/rss/)、[Cloudflare Git 集成](https://developers.cloudflare.com/pages/get-started/git-integration/)、[Buffer API schema](https://developers.buffer.com/reference.html)、[X 字符计数](https://docs.x.com/fundamentals/counting-characters)。

## 基线、身份和补偿

- 启用基线使用 `syndication.config.json` 里的完整 Git 提交 SHA。基线中已公开的文章进入历史记录，包括以后被编辑、改网址或撤下再公开的文章。基线中的草稿仍可在首次公开时自动入选。初次公开时早于基线 UTC 日期的文章视为历史导入。
- 迁移稿如果沿用历史日期，会被日期规则排除。如果迁移稿写成近期日期、同日导入，或无法从日期分辨，请在首次公开的同一提交给 Markdown 添加可选的 `syndicate: false`。这一项由迁移维护者处理，现有 CMS 字段和日常发布步骤无需调整。已有草稿的发布日期如果早于基线，准备正式发布时可在现有日期字段填写本次的发布日期。
- 常规重命名由 Git 追踪。重命名时如果同时大幅改写，尽量先独立提交改名。Git 无法判定的同提交删除加新增会暂停该新条目的分发。跨提交删除再以新路径重建、复制后删旧稿等做法，请在部署前在 `renames` 登记 `"src/content/zh/新路径.md": "src/content/zh/旧路径.md"`。Git 无法单靠内容可靠辨认这种操作，先登记能保留邮件 GUID 和社交渠道账本身份。维护重命名前后的站内跳转仍属于网站 URL 维护。
- 创建账本后保留基线与 `main` 第一父历史。CMS 的正常提交、普通合并、生产重新部署和工作流重跑均可重新算出相同身份。历史重写或替换基线会停止社交发送。回退前先暂停两套发送。
- 定时在 UTC 每 3 小时的第 23 分钟补偿。GitHub 默认只留一个 pending，同组新任务会替换旧 pending。`cancel-in-progress: false` 保护正在运行的任务。各任务都扫描最新的 `main`，被替换或平台取消的触发可由后续任务补偿。保留一个等待任务已足够。GitHub 也提供 `queue: max`，最多 100 个等待任务。公开仓库 60 天无活动时 GitHub 可停用定时工作流，恢复发文时在 Actions 核对状态。 [GitHub concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) · [GitHub schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)
- 最多每轮提交 3 篇，最多可设 10 篇。后续定时任务按首次公开时间处理剩余文章。每篇首次自动处理时固定目标渠道，后来添加的 Facebook 不会补投已处理过的文章。暂停某个渠道可从配置中移除，已有待发记录保留。

### Buffer 状态

| 状态 | 含义与处理 |
| --- | --- |
| `pending` | 明确尚未提交或明确被限流、队列额度拒绝。按 `Retry-After` 或下一轮重新尝试 |
| `submitted` | 已取得 Buffer Post ID，Buffer 报告排队或发送中。按 ID 查最终状态 |
| `sent` | Buffer 报告已发送，保存 Post ID 与服务返回的发送时间。需要检查平台展示时，在 Buffer 的 Sent 列表打开原帖 |
| `failed` | 明确拒绝、渠道不可用或 Buffer 报告发布失败。诊断在 Actions 运行摘要 |
| `unknown` | 可能已提交，例如请求超时、HTTP 5xx、运行中断、状态长期无法确认。停止自动重发，先在 Buffer 和社交平台核对 |

请求发送前，Git 账本必须先记录 `unknown` 和尝试时间。即使运行在收到响应前后中止，下一轮也不会再创建同一帖子。若只读检查或连接建立前失败，未提交的项目仍可自动补偿。未找到一个明确结果的帖子，尤其是短链或返回不全时，在判断能否补发前检查 Buffer 队列、Sent、Failed 以及平台账号。该方案依赖运营核对来处理不确定结果，Buffer 文档的 `CreatePostInput` 未提供幂等键。 [Buffer 错误模型](https://developers.buffer.com/guides/error-handling.html) · [Buffer 限流](https://developers.buffer.com/guides/api-limits.html)

## 一次性配置

### GitHub 和 Cloudflare

在 GitHub 仓库 **Settings → Secrets and variables → Actions** 下配置。

| 位置 | 名称 | 配置 |
| --- | --- | --- |
| Secrets | `BUFFER_API_KEY` | 从 Buffer 复制 API Key |
| Variables | `BUFFER_ORGANIZATION_ID` | Buffer 组织 ID。账户只有一个组织时可自动识别 |
| Variables | `BUFFER_CHANNEL_IDS` | 默认渠道，只填目标 X ID。多个 ID 用逗号分隔 |
| Variables | `BUFFER_CHANNEL_IDS_ZH`、`BUFFER_CHANNEL_IDS_EN` | 可选，指定语言的渠道列表。未设置时沿用默认列表。若只想自动分发中文，只设中文变量并留空默认列表 |
| Variables | `BUFFER_TEST_CHANNEL_IDS` | 可选，额外授权人工操作的测试渠道。不会进入自动发送列表 |
| Variables | `SOCIAL_DISTRIBUTION_ENABLED` | 仅 `true` 开启自动调用 Buffer，默认留空或 `false` |
| Variables | `SOCIAL_DISTRIBUTION_MANUAL_ENABLED` | 仅 `true` 允许人工发帖或补发。还需要在运行界面填写文章、渠道并勾选确认 |
| Variables | `BUFFER_MODE` | 默认 `shareNow`。希望按 Buffer 时段排队可设 `addToQueue` |
| Variables | `SOCIAL_HASHTAGS` | 可选，`true` 才从文章标签添加话题 |
| Variables | `MAX_ARTICLES_PER_RUN` | 默认 3，允许 1–10 |

维护者选定基线时，先让已确认合并的版本部署，再以开始前的 `main` 提交作为基线。用一个独立提交配置基线并部署，检查专用 Feed 无历史条目且生产索引显示相同基线。Cloudflare 构建需能读取至基线的 Git 历史，Pages 浅克隆时构建会尝试补齐。检查生产分支为 `main`，命令为 `npm run build`，输出为 `dist`。在 Cloudflare **Settings → Builds → Branch control** 的预览分支规则中排除 `syndication-state`，以免账本产生预览构建。

在 **Actions → Distribute new articles** 选择 `main`，勾选确认并运行 `initialize-ledger` 一次。这建立只有 `ledger.json` 的 Git 分支 `syndication-state`。只读操作使用 `contents: read`，账本操作的 job 使用 GitHub 自带的 `GITHUB_TOKEN` 和 `contents: write`，无需添加 PAT 或 Cloudflare API Token。保留 `main` 的现有保护，避免人工删除、重写账本。账本分支随公开仓库可读，包含分发记录、发布链接、渠道 ID 和 Buffer Post ID。密钥、订阅者数据和服务商原始错误正文不写入账本、日志或网页。 [Cloudflare 分支控制](https://developers.cloudflare.com/pages/configuration/branch-build-controls/) · [GitHub 工作流权限](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)

### Buffer

1. 用目标 X 账号登录并在 Buffer **Connect a Channel** 授权 X。可选的 Facebook 连接项选 **Facebook Page**，使用拥有 Page 所需权限的账号。连接过期时先在 Buffer 重新连接。
2. 在 Buffer **Settings → API** 生成个人 API Key，直接保存进上述 GitHub Secret。运行 `list-channels` 确认组织、渠道 ID、服务类型与授权状态，再写变量。常规运营只配置 X。确认连接处于可用状态，排队模式还需设置发送时段并启动队列。
3. 用 `dry-run` 预演一篇，检查中文、链接和长度。该操作不会访问 Buffer 或改账本。网站现有 canonical、Open Graph、`summary_large_image` 为 X 提供抓取信息。X 用 t.co 包装链接，正文中的有效 URL 按 23 加权字符计。Buffer 的 `buff.ly` 是独立渠道设置，可把测试渠道设为 **No Shortening** 保留更容易核对的原链接。X 在发送后自行抓取卡片，Facebook 的卡片由 Buffer/Meta 生成，平台可能省略图片或采用缓存。
4. 获得作者对真实测试的明确授权后，可保持自动开关关闭，临时启用人工开关，以 `publish-one` 在指定测试渠道发单篇已上线文章。检查 Actions 的 Post ID、Buffer 最终状态、真实平台链接和卡片，然后关闭人工开关。软件验证使用官方文档及模拟服务，真实账号、队列、短链和卡片仍需这一步确认。

参考 [授权渠道](https://support.buffer.com/articles/connecting-your-channels-to-buffer-HvWLgAJvL9)、[API Key](https://developers.buffer.com/guides/authentication.html)、[排队和状态](https://developers.buffer.com/guides/posts-and-scheduling.html)、[短链接](https://support.buffer.com/articles/shortening-and-unshortening-links-dgev2p41yY)、[链接卡片](https://support.buffer.com/articles/attaching-images-videos-and-other-media-to-your-posts-eudySt0TnS)。

### Brevo Newsletter

1. 沿用博客现有通过双重确认的中文订阅列表和认证发件人。在 Brevo **Integrations → RSS campaign → Create Integration** 输入 `https://reasonforhim.com/zh/distribution.xml`，点 **Load RSS feed**。先选 **Save and keep inactive**。如果空 Feed 无法预览，用独立测试列表和含样例的新 Feed 预览模板，生产 Feed 保持干净。
2. 选 **RSS Default Template**，在设计器保留针对 `params.items` 的可重复内容块。用 `{{ item.TITLE }}`、`{{ item.DESCRIPTION | safe }}`、`{{ item.LINK }}` 生成标题、摘要和「阅读全文」。如需要日期与封面，用 `{{ item.PUBDATE }}` 和 `{{ item.ENCLOSURE }}`，在无封面的项目隐藏图片块。建议中文正文 16 px、行高约 1.6，移动端预览中文换行、字距和按钮。主题可用「为何是祂｜新文章」。把英文默认页脚改成中文，保留 Brevo 的退订链接并核对发件人信息。设计器可用 **Unsubscribe link**，模板语言支持 `{{ unsubscribe }}`。
3. 初次核对选择 **Manually** 只生成草稿。测试列表只放已授权的地址。用测试 Feed 观察首篇、标题或日期修订、URL 改动以及两篇连续新增是否符合预期；核对每个草稿中过去已通知的文章没有再进入邮件。足够验证后再切到已确认订阅列表。若生产空 Feed 无法通过初始验证，可等第一篇获准发布的正式文章出现在 Feed 后再载入，在人工模式核对首封是否已生成。首篇是否需要手动补发以 Brevo 实际活动记录为准，每篇只通知一次。
4. 作者授权后，选 **Automatically** 并启用集成。在 **Specific days of the week** 选择每一天，设置稳定的收件时段并检查账户时区。Brevo 文档说明一般需在检查前至少 1 小时有新文章，每天检查一次，实际可能跨到次日。一次 Campaign 最多拉取 10 篇，建议保留模板上限 10。发布超过 10 篇或 Feed 延迟跨过发送窗口时，先核对实际活动再决定人工补发。

专用 Feed 使用不随 URL 变化的 GUID 和不可变的首次公开时间，链接指向当前 canonical，封面以 RSS enclosure 提供。Brevo 文档确认仅在检测到有新内容时创建 Campaign，并可自动发送或生成草稿，但没有公开首轮游标初始化、GUID 与日期变更的精确比较规则，也没有承诺相同时间戳、改 URL 或补发时的行为。实际账户验证是开启真实自动发送前的必要检查。邮件使用 Brevo 原生 RSS 集成。 [RSS Campaign](https://help.brevo.com/hc/en-us/articles/360013130059) · [模板字段](https://help.brevo.com/hc/en-us/articles/360016993299) · [退订链接](https://help.brevo.com/hc/en-us/articles/9741388688402)

## 人工处理、停用与回滚

- 到 **Actions → Distribute new articles** 看运行摘要。部署延迟优先看 Cloudflare 最新生产构建。API 临时错误不必重复点发帖，可观察下一次补偿。
- 有 Post ID 的失败先在 Buffer 对原帖处理，再通过 `reconcile-one` 刷新账本。没有 ID 的 `unknown` 若找到原帖，核实文章与渠道后提供该 Post ID。只有核实未发且无原帖时，才临时打开人工开关并运行 `retry-one`。该动作以同一文章和渠道为目标，已有 `sent` 的渠道不会补发。
- 紧急停用 Buffer 时设两个发送变量为 `false`，取消正在运行的发送任务，并到 Buffer 检查已入队项目。已经提交给 Buffer 的帖子可能继续发布，取消队列需在 Buffer 完成。
- 停用邮件时在 Brevo 单独暂停 RSS integration，并检查待发送的 Campaign。GitHub 开关不控制 Brevo。已经发出的邮件和帖子不能通过 Git 回滚撤回。
- 若需回退网站代码，在两个发送端停用后回退相应代码。保留原基线 SHA 与账本分支供恢复，禁止用空账本代替历史记录。恢复自动化前核对暂停期间积压与两边历史，先预演再按授权恢复发送。

## 免费额度与已知边界

- Buffer 免费支持 1 把 API Key、最多连接 3 个渠道、每渠道 10 个待发布位置。官方 API 免费额度为每 15 分钟 150 次、每 24 小时 600 次、滚动 30 天每个已解锁渠道 1,000 次，合计最多 3,000 次。单开 X 即 1,000 次。空闲补偿不访问 Buffer。假设每月 8 篇、一个渠道，每篇最多用 1 次渠道查询、1 次提交、1 次正常状态核实，约 24 次请求，另计人工检查或较长排队。 [Buffer API 限流](https://developers.buffer.com/guides/api-limits.html) · [Buffer 免费套餐](https://support.buffer.com/en-us/articles/buffer-pricing-and-features-6pJrOPuzIt)
- Brevo 免费每日 300 封，包含其他当天发出的邮件，要为确认邮件留余量。按 100 名确认订阅者、一个发送日一期估算约占 100 封。超过每日余额会影响完整送达，不能假定 Campaign 自动把剩余联系人次日补齐；查看账户 RSS 集成权限、Campaign 记录和剩余额度。 [Brevo 免费版限制](https://help.brevo.com/hc/en-us/articles/208580669) · [Brevo 发送额度](https://help.brevo.com/hc/en-us/articles/8292912279954)
- 公开仓库的 GitHub 标准托管 runner 免费，每天约 8 次定时检查及内容 Push。Cloudflare Pages 免费为每月 500 次构建，定时任务只读取生产站，账本分支应排除预览构建。现有规模的预估增量成本为 0。 [GitHub Actions 计费](https://docs.github.com/en/actions/concepts/billing-and-usage) · [Cloudflare Pages 上限](https://developers.cloudflare.com/pages/platform/limits/)
- 日期按 UTC 解释。未来日期文章到期后，社交可在定时检查时处理已部署的版本，静态 Newsletter Feed 会在下一次 Cloudflare 构建后纳入。现有网站页面的未来日期可见规则沿用原站，未来日期不构成提前发布正文的保密设置。
- 首次公开后又撤下、删除，且从未在 Cloudflare 获得可验证的线上版本时，系统不会向外部分发。暂停开关期间保持公开的合格文章会在恢复后被社交批次处理。Brevo 的发送恢复由其集成状态和实际 Campaign 记录决定。
